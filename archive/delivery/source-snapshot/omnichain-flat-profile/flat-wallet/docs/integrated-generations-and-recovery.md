# Integrated generations, manual authorization and DeFi recovery

The current source selects one private mixed portfolio keeper/journal before
admission. TOP_UP/EXIT expiry can reach a positively proven, durably retained
no-dispatch state. Only a new explicit owner review/confirmation advances that
same operation to its new epoch; request, note, amount, recipient and history
remain original. Ordinary or post-submission UNKNOWN is not reset. GRAPH uses
its original execution and cutoff recovery; it does not receive note-epoch reset.

The immutable catalogue durably binds original request IDs and references to
one generation before preparation/confirmation. It creates no competing keeper
on an authority and never rewrites old registry identities. Original recovery
remains routed to its old generation when a successor is unavailable. A fault
in the catalogue's own authenticated route index retains the app-wide activity
fence; no stale data authorizes a new action. This is original surviving-object
checkpoint recovery, not whole-host, password or root-key restoration.

Manual EVM-vault GRAPH needs a genuine private owner approval and exact-only
application mode. Each prepare/execute/reconcile/recover grant is one-use and
bound to its canonical body and original target. The old broad manual bearer
does not gain GRAPH access. Execution retains the original funding/cutoff
checks; reconciliation/recovery can use the retained original after cutoff or
provider failure without a new graph, send or owner-online requirement.

The same HTTP/Node/browser read path validates the versioned catalogue view,
shows each pool/generation separately and retains missing amounts as unknown.
No balances are summed across generations and no note is implicitly migrated.
Generation DeFi composition fixes its original service set for its lifetime;
new catalogue entries cannot expand an existing grant, including empty-body
reopen. Exact original share EXIT IDs route to the original vault service.
Lost sends stay unresolved until original reconciliation, without resend.

Separate vault-position rows require the exact original generation, asset IDs,
head and private share balance. A between-read head advance suppresses the
estimate; an unrelated unavailable generation need not suppress a correctly
joined old one. Estimates remain conservative and non-spendable. Null original
journal request IDs mean unknown contents, never zero obligations.

Evidence includes physical production imports, real encrypted lifecycle stores
with explicit synthetic lower state/proof/transaction observations, genuine
session/SDK paths and actual read-only loopback HTTP. No funded acceptance,
visual browser, mobile hardware custody or external audit is claimed for this
source addition. Root keys remain owner-side; common-host trust and systemic
metadata correlation limits remain. The inactive eight-pool contract candidate
and existing global64 ceilings do not establish unbounded wallet operation.

The separately versioned combined audit lifecycle is now installed. It stages
immutable unsigned intent before the full reciprocal pre-key audit, retains a
new full reciprocal audit after signature persistence, and uses one final full
audit for exact reuse. Original heads, inventories and 30-second guards remain.
Post-key/final-await failures poison shared custody. An early rejection can leave
unsigned staged intent, whose existing retry fence remains. It has focused
source/host review evidence but no new loaded native success yet.


## Generation admission metadata and SDK selection

The catalogue owner read includes `freshAdmissions: { version: 1, fenced, routes: [{generationId, assetId}] }`.
The list is the exact authenticated catalogue preference, with at most eight
unique registered original asset IDs joined to their exact generation IDs. It is route-selection metadata only: it
does not certify balance, capacity, chain/proof validity, consent or authority.
The producer rechecks its own durable route index and checks its original
policies for append uncertainty, admission fences and preference disagreement.
A failed route-index read latches the existing storage fault; the original
balance/recovery view remains separately visible.

The shared browser/Node codec accepts this bounded, explicitly versioned optional extension. Older
V2 reads without it remain readable, but the updated SDK cannot infer a fresh
TOP_UP route or enable GRAPH from an absent preference. Generation-array order never
chooses a route. A stale but internally consistent host pointer is not a client
chain-verification claim: the original server still rejects a new TOP_UP on a
superseded pool before child preparation or owner review. Upgrade producer and
shared codec together: old strict clients reject the extended payload rather
than silently accepting new fields. No HTTP route, bearer or capability is added.

New TOP_UP choices include only current IDs from that list, even where several
pools have the same symbol. An original prepared TOP_UP can finish on its old
route, and an original PREPARING continuation must match one exact original
request/asset row. It never adopts the successor or accepts a replacement ID.
A reported admission fence blocks TOP_UP and GRAPH choices. Healthy current
original EXIT remains separately selected, including the established PARTIAL
catalogue case, with its exact generation, pool, domain and observed head.
Reconciliation remains ID-bound and never resends.

These are bounded source/host behavior guarantees. The eight-route and global64
limits, all original journal/inventory poisoning and monotonicity checks,
immutable bindings and note ownership are unchanged. Genuine V2 phase-1 and
phase-2 rollout acceptance is still a separate gated native/proof run; source
checks and a loopback SDK read do not establish funded rollover or unbounded use.
